COPS test bench

What this is. COPS is a fleet of 18 governance COPs. Each COP answers one behavioural question about an AI agent's activity, such as "is resource consumption within entitlement?". Every COP reads the agent's telemetry and authoritative records (policies, quotas, registries), forms a finding, has that finding checked by independent verifiers, and may propose an action. Enforcement is in dry-run: an action is recorded, never executed.

Ten COPs use a language model to investigate: it plans, asks for tools, and proposes a finding that the verifiers then check. Eight COPs are rule-based and make no model call. Each COP was tested on three fictional cases: a normal one, an abnormal one, and one where the evidence it needs is missing. Each case's expected outcome was fixed before it ran and never shown to the COP.

Where a result comes from: LIVE real model calls, recorded with request ids and measured tokens REPLAY the recorded real replies fed back in under the current code (tools and verifiers re-run, no model call, no cost; never counted as a new live call) NEW LIVE CALL a fresh model call made after the fixes (none yet) DETERMINISTIC rules only, run for real, no model SIMULATED scripted replies

Verdicts: PASS ran, matched the expected outcome, stayed within authority FAIL wrong finding, or did not run correctly INCONCLUSIVE held back where a definite answer was expected UNTESTED not run

What happened to the action: NO ACTION PROPOSED the COP proposed NONE PROPOSED, AWAITING APPROVAL waiting for a human PROPOSAL WITHDRAWN the finding failed verification, so its action was withdrawn REJECTED BY AUTHORITY not permitted for this COP or mode (a substitute may stand) APPROVAL REJECTED a reviewer said no AUTHORISED (DRY-RUN) allowed; a dry-run adapter recorded what it would do, nothing applied EXECUTED applied by the enforcement gateway (here only the mock one) FAILED OR UNCONFIRMED the gateway failed or the outcome was not observed

Not every abnormal finding calls for an intervention: an ALERT for a reviewer, or WATCH, is often the right action. No real blocking, notification or other external effect exists in this runtime.

Why cases are inconclusive

An INCONCLUSIVE is correct when the evidence the COP needs is missing. It is a problem when a definite answer was expected. Decision status, root cause and evaluation verdict are kept separate; one case can have several root causes.

Before and after the root-cause fixes

The original result is the one recorded before the fixes (test_bench_results_before_fixes.json). The current result says where it came from. A replay re-uses the recorded real model replies; it is never presented as a new live call.
